# Silver Surfer — Knowledge Priming

Knowledge Priming generates and maintains structured, up-to-date knowledge about your codebase(s) — so AI coding agents can work grounded in real context instead of re-reading entire repositories on every task.

It works across one repo or many (a "team/project"), and is tool-agnostic — the same agent/skill definitions are placed differently depending on whether you use GitHub Copilot, Claude Code, or Cursor. See the "Tool Placement Reference" table at the bottom of each agent file for the exact mapping.

This repo is one half of a split. The other half — [`Silver_Surfer_Workflow`](https://github.com/specscout27/Silver_Surfer_Workflow) — contains the Epic, User Story, and Tech-Details agents that turn this knowledge into implemented code. Workflow treats this repo as an optional external dependency: it runs standalone if this isn't installed (falling back to direct codebase search), and runs knowledge-grounded if it is. Knowledge Priming has no dependency in the other direction — it doesn't know Workflow exists.

---

## How It Fits Together

```
1. Knowledge Priming Agent   → generates the initial knowledge base (run once per repo/team)
2. Update Context Agent      → keeps that knowledge base in sync with new commits (run whenever code drifts)
```

Any downstream consumer — this repo's own `smart_context_loading` skill, `Silver_Surfer_Workflow`'s agents, a custom agent you build yourself, or another workflow framework entirely — reads what these two agents produce.

---

## Where Knowledge Lives

All knowledge generated by these agents is written to a **dedicated sibling repository** — never inside your source repos.

```
[Workspace_Root]/                          <- workspace root
├── Silver_Surfer_Knowledge_Priming/       <- this repo (agents + skills only)
├── [Team_Or_Project_Name]_Knowledge/      <- generated knowledge repo, sibling to this repo
│   ├── index.md                           <- team/project-level index
│   ├── features/                          <- cross-service feature flows
│   ├── sessions/                          <- epic/story session files (for @continue, written by Workflow)
│   ├── summary/                           <- story summary/handoff files (written by Workflow)
│   ├── repo-map.md                        <- maps each service -> its source repo path
│   ├── [Service_Name_1]_Knowledge/        <- one repo's knowledge (index.md + modules/ and/or features/+submodules/ and/or infra/, per detected facet)
│   └── [Service_Name_2]_Knowledge/
└── [your other sibling repos...]
```

Each **service** = one repository. The Knowledge Priming Agent will find or create this Knowledge repo automatically (always asking for your confirmation first), and every other agent reads/writes to it via the same convention.

## The Agents

| Agent | File | Purpose |
|---|---|---|
| **Knowledge Priming** | `.github/agents/Silver_Surfer.knowledge_priming.agent.md` | Generates the knowledge base from scratch for one or more repos |
| **Update Context** | `.github/agents/Silver_Surfer.update_context.agent.md` | Detects drift since the last known baseline and surgically refreshes the knowledge base |

Both are opt-in — neither runs automatically. You invoke the one you need.

### Skills

| Skill | Invoked By | Scope |
|---|---|---|
| `code_to_knowledge` | Knowledge Priming Agent | Per-service generation (module-centric / feature-centric / infra-unit-centric) |
| `service_to_knowledge` | Knowledge Priming Agent | Team/project-level synthesis across services |
| `repo_context_update` | Update Context Agent | Per-service drift detection and surgical update |
| `service_context_update` | Update Context Agent | Team/project-level drift detection and update |
| `smart_context_loading` | Any consumer (internal to this repo's own vocabulary — see below) | Surgical, read-only query of the Knowledge repo by an external orchestrator |

## 1. Knowledge Priming Agent — First-Time Setup

**When to run it:** Once per repo, before anything else. Re-run it if you add a brand-new repo/service to the team/project.

**What it does:**
1. Confirms git guardrails on each target repo (clean tree, on `main`/`master`, up to date with `origin`).
2. Locates or creates the sibling `[Team_Or_Project_Name]_Knowledge` repo (always asks for confirmation before creating).
3. For each repo in scope, generates per-service knowledge (`code_to_knowledge` skill) — module-centric for backend/infra, feature-centric for frontend.
4. Synthesizes team/project-level knowledge across all services (`service_to_knowledge` skill) — cross-service features, tech stack, architecture narrative.
5. Writes/updates `repo-map.md` so future agents know where each service's source code actually lives.

**How to invoke:**
> "Run the Knowledge Priming Agent on `[repo path or list of repos]`"

You'll be asked to confirm the Knowledge repo location/creation, confirm the discovered repos, and approve each generated file before it's written.

## 2. Update Context Agent — Keeping Knowledge Fresh

**When to run it:** Any time code has moved on `origin/main` since the knowledge base was last generated/updated. Also invoked automatically (with your confirmation) at the start of `Silver_Surfer_Workflow`'s Epic Agent and User Story Agent runs, when that repo is installed alongside this one.

**What it does:**
1. Reads `repo-map.md` in the Knowledge repo to resolve each service to its source repo path.
2. Compares each service's current `origin/main` against the baseline commit recorded in its knowledge.
3. Classifies drift (D0 = none, up through D5 = cross-service major drift requiring manual resolution).
4. Proposes surgical before/after edits to the affected knowledge files — you approve each one (or approve in bulk).
5. Runs a team/project-level pass afterward to refresh cross-service features, tech stack, and the index.

**How to invoke:**
> "Run `@update-context`" — refreshes every service in `repo-map.md`
> "Run `@update-context [service-name]`" — refreshes just one service (plus any dependent team/project-level updates)

If a brand-new repo has appeared in the workspace that isn't in `repo-map.md` yet, Update Context will flag it and tell you to run Knowledge Priming on it — it does not auto-prime new repos.

## Recommended First Run

```
1. Run Knowledge Priming Agent on all repos in your team/project.
2. Try Update Context once with no code changes — confirms the loop works end-to-end.
3. Commit and push the generated knowledge files in the Knowledge repo.
4. Install Silver_Surfer_Workflow alongside this repo to plan epics, write user stories, and implement grounded code.
```

## Installing via CLI or Plugin

**Any tool (Copilot, Claude Code, Cursor) via the CLI:**

```
npx github:specscout27/Silver_Surfer_Knowledge_Priming init --target claude|cursor|copilot|all
```

This vendors the agent/skill content into `.knowledge-priming/` in your project, then writes a thin wrapper file per tool at the exact paths each agent's own "Tool Placement Reference" table specifies — no manual copying. Re-run it later to refresh the vendored copy.

**Claude Code specifically, as a plugin** (no vendoring — reads this repo directly):

```
/plugin marketplace add specscout27/Silver_Surfer_Knowledge_Priming
/plugin install knowledge-priming@Silver_Surfer_Knowledge_Priming
```

Gives you the `knowledge-priming` and `update-context` skills (human-invoked only — they never auto-fire) plus native subagents of the same names, and the auto-invocable `knowledge-query` skill any custom Claude Code agent can pick up to query the Knowledge repo without reading any of this framework's own docs first.
